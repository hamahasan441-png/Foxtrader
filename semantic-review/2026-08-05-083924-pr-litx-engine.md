# LIT X Institutional Framework analysis module

Adds an additive, opt-in "LIT X" analysis pipeline that orchestrates the app's existing SMC detectors (structure, order blocks, FVGs, liquidity, sessions, R:R optimizer) and three new first-class primitives (displacement, mitigation block, premium/discount) into a staged Market-Context → Sweep → Shift → POI → Entry flow, scored by an 11-factor confidence model and surfaced on a standalone screen reached from the chart top bar. The engine is pure/synchronous and unit-testable; the ViewModel fetches candles + HTF context and runs it off the main thread. The branch also merges main's chart redesign (immersive mode, indicator panes) and wires a new nav route `litx/{symbol}/{timeframe}`.

Watch for: the R:R gate and R:R confidence factor are degenerate because the reused optimizer always returns exactly the requested minimum (**confirmed**); a tradeable signal can validate with neither a liquidity sweep nor a market shift, contradicting the stated pipeline (**confirmed**); the "detect latest" displacement actually returns the strongest bar in the window, which can mislabel a stale CHOCH as a strong MSS (**confirmed**); and the nav route interpolates the raw symbol without encoding (**possible** — matters only if slash-form symbols reach the chart).

**Verdict**: NEEDS_CHANGES

## High-level view

The pipeline's directional intent, POI selection (mitigation block > fresh OB > unfilled FVG), premium/discount zoning, and confidence normalization are sound and handle degenerate data (empty/short/flat/zero-volume) without crashing. The confidence score is a weighted average normalized by total weight, so it cannot exceed 100 and the grade thresholds map correctly.

The weak point is the entry/validation gate. It leans on `RiskRewardOptimizer`, which by construction always produces a setup whose realized R:R equals the requested minimum — so `setup.valid` is always true and the R:R confidence factor is a constant. The gate therefore reduces to "POI retested + grade passes," and nothing forces the sweep or the market shift that the framework's own narrative promises. A signal can be emitted from trend bias alone, and its rationale will still claim a CHOCH that never occurred.

The new primitives are non-repainting and index-safe, but `DisplacementDetector.detectLatest` returns the strongest impulse in the lookback rather than the most recent one; because `MssClassifier` uses that displacement to upgrade a CHOCH to a "strong" MSS, a stale impulse can inflate both the structure/displacement factors and the shift strength.

Nav round-trips correctly for every `Timeframe` label (case-sensitive, so `1m`/`1M` stay distinct), but the route builder never encodes the symbol; a symbol containing `/` or a space would break path matching. The chart-redesign merge into `ChartScreen.kt` / `FoxNavHost.kt` is internally consistent — imports and the new callback line up, no compile risk found.

<summary>Issues (7)</summary>

1. **R:R gate/factor degenerate** — `RiskRewardOptimizer` builds TP at exactly `minRR * stopDistance`, so realized R:R always equals `minRR` and `setup.valid` is always true for ≥20 bars; the R:R factor is a constant 70. Derive targets from structure/POI (or opposite-side liquidity) instead of a minRR-scaled TP, and don't treat `setup.valid` as a gate.
2. **Signal validates without sweep or shift** — the `validated` predicate omits `sweep != null` and `shift.present`, so a signal can fire from trend bias + POI retest alone. Add the sweep/shift requirement to the gate (or to grading) so it matches the stated pipeline.
3. **Rationale claims a CHOCH that didn't happen** — `buildRationale` prints "CHOCH" whenever `strongShift` is false, including when there is no structure break at all. Pass `shift.present` and describe trend continuation when no shift exists.
4. **`detectLatest` returns strongest, not latest** — displacement selection keeps the max `atrMultiple` across the lookback, so a stale impulse can wrongly upgrade a recent CHOCH to a strong MSS and inflate displacement scoring. Select by most-recent index or require proximity to the shift's `breakIndex`.
5. **Symbol not URL-encoded in nav route** — `FoxRoutes.litx` interpolates the raw symbol into `litx/{symbol}/{timeframe}`; a `/` or space (e.g. TwelveData "EUR/USD") adds a path segment and breaks arg matching. Encode with `Uri.encode` (or guarantee concatenated symbols).
6. **Stage can skip SHIFT_CONFIRMED** — `poiTapped` is evaluated before the shift branch, so the linear pipeline strip can show POI_TAPPED without a confirmed shift. Reorder or gate POI_TAPPED on a prior shift.
7. **No stale-result guard in ViewModel** — `analyze()` launches without cancelling a prior in-flight job or verifying the symbol before applying; a mid-analysis symbol change could apply a stale result. Track the job and cancel/guard on relaunch.

### R:R validation and the R:R factor carry no information

`LitXEngine` calls `riskRewardOptimizer.optimize(candles, intended, config.minRiskReward)` and then uses two outputs: `setup.valid` in the `validated` gate, and `setup.riskRewardRatio` in the confidence input

```kotlin
riskReward = (setup.riskRewardRatio / config.minRiskReward.coerceAtLeast(1e-9) * 70.0)
    .roundToInt().coerceIn(0, 100),
```

But `RiskRewardOptimizer.optimize` constructs the target as `tp1 = entry ± stopDistance * minRR` with `risk = stopDistance`, so `riskRewardRatio = (stopDistance * minRR) / stopDistance = minRR` exactly, and `valid = rr >= minRR` is always true once there are ≥20 candles (`RiskRewardOptimizer.kt:44-73`). Passing `config.minRiskReward` as the `minRR` argument makes this circular:

- `riskReward` factor is always `minRR/minRR * 70 = 70`, regardless of how good the actual reward-to-risk is.
- `setup.valid` is a constant `true`, so the `validated` gate below never depends on it.

The `minRiskReward` config knob and the R:R confidence factor therefore have no observable effect. Fix direction: compute the target from a real structural objective (the selected POI's far edge, or the opposite-side liquidity pool the setup is targeting) so the ratio varies, and stop using `setup.valid` as a gate condition.

### The entry gate never requires the sweep or the shift the pipeline promises

```kotlin
val validated = setup.valid && retestScore >= 70 &&
    LitXConfidenceScorer.meets(confidence.grade, config.minGrade)
```

With `setup.valid` always true, validation reduces to "price is inside/near the POI band and the grade passes." `intended` can be derived purely from `structure.bias` when no shift exists (`shift.direction ?: when (structure.bias) …`), and neither `sweep != null` nor `shift.present` appears in the predicate. So a VALIDATED, tradeable `LitXSignal` can be produced with no liquidity sweep and no market-structure shift — directly contradicting the documented Sweep → Shift → POI → Entry framework. The non-shift factors (POI up to ~98, retest 90, volatility/session 90, R:R 70, HTF-aligned trend 80) can push the weighted average to A even while `sweepStrength` and `structureQuality` sit at their floor values. Fix direction: require `shift.present && shift.direction == intended` (and ideally an aligned sweep) in the validation predicate, or make the confidence model unable to reach the min grade without them.

### Rationale asserts a CHOCH even when no break occurred

`buildRationale` is called with `shift.isStrong`:

```kotlin
val shiftTxt = if (strongShift) "MSS (displacement-confirmed)" else "CHOCH"
```

`strongShift` is only the *strong* flag; when it is false the text is unconditionally "CHOCH." But `intended` may have come from `structure.bias` with `shift.present == false`, in which case there is no CHOCH at all. Signals taken on trend bias will narrate a structure break that never happened, which is misleading on a screen whose whole value is explaining institutional reasoning. Pass `shift.present` into the builder and describe trend continuation when there is no break.

### DisplacementDetector returns the strongest bar, not the latest

Despite the name `detectLatest` and the "most recent displacement leg" doc, selection keeps whichever bar has the highest `atrMultiple`:

```kotlin
if (best == null || atrMult > best.atrMultiple) { best = Displacement(... startIndex = i ...) }
```

Indexing and non-repainting are fine — the scan starts at `max(1, size - lookback)`, reads `candles[i-1]` (safe since `i >= 1`) and guards `candles[i+1]` against the end of the series, so no future bar beyond the last closed candle is read. The behavioral problem is staleness: the strongest impulse in a 30-bar window may be far from the current shift. `MssClassifier.classify` upgrades a CHOCH to a "strong" MSS whenever `displacement.direction == shift.direction && atrMultiple >= threshold`, without checking that the displacement is near the break. A large impulse 25 bars ago that happens to share the CHOCH's direction will mark a fresh, unrelated CHOCH as displacement-confirmed and simultaneously inflate `displacementStrength`. Select by most-recent qualifying index, or require the displacement to sit at/after the shift's `breakIndex`.

### Nav route does not encode the symbol

`FoxRoutes.litx(symbol, label)` builds `"litx/$symbol/$timeframeLabel"` with no escaping, against the pattern `litx/{symbol}/{timeframe}` (`StringType` args). Every `Timeframe.label` is slash-free and case-distinct, so the timeframe round-trip via `Timeframe.fromLabel` is safe and the M15 default only triggers on a genuinely unknown label. The symbol is the exposed edge: this codebase uses concatenated symbols in-app ("EURUSD", "BTCUSDT"), but the TwelveData layer documents slash forms ("EUR/USD", "BTC/USD"). If a slash- or space-bearing symbol ever reaches `state.symbol`, the extra path segment makes the route fail to match (or bind the wrong args), and the LIT X screen silently won't open. Encode with `Uri.encode(symbol)` in the builder (NavType decodes on the way out), or assert the concatenated form. Worth confirming which symbol format the chart's `state.symbol` actually holds.

### Stage strip can show POI_TAPPED without a confirmed shift

```kotlin
val stage = when {
    validated -> LitXStage.VALIDATED
    poiTapped -> LitXStage.POI_TAPPED
    shift.present && shift.direction == intended -> LitXStage.SHIFT_CONFIRMED
    sweep != null -> LitXStage.SWEEP_DETECTED
    ...
}
```

`poiTapped` is tested before the shift branch, so price sitting in a POI band with no shift yields POI_TAPPED — a later stage on the enum-ordered progress bar than the SHIFT_CONFIRMED it supposedly follows. Cosmetic, but the strip implies linear progression. Reorder, or gate POI_TAPPED behind a prior shift.

### ViewModel has no stale-result guard

`analyze()` launches directly in `viewModelScope` with no stored `Job` to cancel and no check that `_uiState.value.symbol` still matches before applying the result. The heavy work is correctly moved to `defaultDispatcher` and errors are caught, so the concern is narrow: if `analyze()` is invoked again (symbol change) before the first completes, both run and the later-finishing one wins, which need not be the newest request. In practice the LIT X VM is scoped per nav back-stack entry and `LaunchedEffect` keys on `symbol`/`timeframe`, so a new symbol usually means a new VM — low real-world risk, but a `job?.cancel()` before relaunch (or a symbol check before `update`) removes it entirely.

### Test coverage

The suite covers the safe cases well: insufficient/empty data, a flat market producing no signal, a trending smoke run asserting 11 factors, displacement detect/none, premium/discount/equilibrium classification, the CHOCH→MSS upgrade, and the scorer's 0/100 bounds and grade thresholds.

Not tested: a fully VALIDATED signal path (so the degenerate R:R gate and the no-sweep/no-shift validation both slip through untested), the 20–49-bar boundary between the ViewModel/engine `MIN_BARS` and the primitives' lower thresholds, the zero-volume `volumeConfirmation` fallback, `MitigationBlockDetector` end-to-end, the premium/discount location bonus in `poiQuality`, and the nav route round-trip with an awkward symbol.
